# How AI was used

A running log of how AI tools were used to build this, kept to show the process honestly. The standing instructions given to the AI agent (code style, tests, always run the code, git rules) are in [../.claude/CLAUDE.md](../.claude/CLAUDE.md).

| Phase | What AI did | What I decided / verified myself |
|------|-------------|----------------------------------|
| 1. Requirements | Read the brief, asked clarifying questions (stack, deploy, git, ownership), drafted REQUIREMENTS.md and ARCHITECTURE.md | Fixed the stack and wrote the standing rules in CLAUDE.md (tests with every change, always run the code, idempotent APIs, atomic transactions, no AI attribution in commits, skills kept out of git); chose 6 countries and kept data-protection law out of scope |
| 1b. Design | Used the repo skills (frontend-design, python-patterns, senior-backend) to draft the design pack and a clickable prototype; screenshot-tested the prototype and fixed the bugs found | Chose no dark mode and each country's own number format; the larger design changes that followed are in 1c and 1d |
| 1c. Decisions | Turned the HR/tech answers into DECISIONS.md, redesigned the prototype in shadcn style (simpler), added the deployment and secrets design (Render demo + AWS App Runner/RDS/Secrets Manager) | Chose shadcn only, App Runner (later replaced by one EC2 server), Docker, demo login; rejected the first prototype look |
| 1d. UI research | Researched filter UX, dashboard overload and SaaS navigation; wrote 07-UI-RESEARCH.md; rebuilt the prototype (v3) and screenshot-tested it on desktop and phone | Asked for left filters, a calmer home page and visible user info; rejected v2 |
| 1e. Decisions | Sent clarifying questions to the hiring team; built an interactive decision book (42 questions with recommendations); read back the answers and updated every design doc; researched hosting regions | Answered all 42 questions; chose two roles, photos and documents, live rates, gender stored only, a separate employee page |
| 1f. Review | Cross-checked every doc against the brief and the decision book; fixed contradictions (stale ARCHITECTURE.md, page size, levels, money precision, "left" status, region, backups, worker container) | Asked for the review and approved the fixes |
| 1g. Deploy plan | Used the senior-devops skill to plan a one-command AWS deploy (CloudFormation stack, GoDaddy DNS, SSM release) and updated 06-DEPLOYMENT.md and DECISIONS.md | Chose the GoDaddy API for DNS, `t4g.small`, and building it at step 15 |
| 1h. Deploy skill | Wrote the `aws-deploy` Claude skill (CloudFormation stack, deploy/start/stop scripts, server scripts, 27 bats tests with stubbed AWS); a mutation check found two test assertions that could never fail, which were fixed | Asked for start/stop to save money, a $10 budget alert, skills instead of repo scripts, and that no credential leaves their machine |
| 2–14. Build | Wrote the FastAPI backend (models, Alembic migration, seed, auth, employees, salaries, insights, files, imports, worker) and 158 pytest tests; split the React frontend off to a parallel subagent that worked from the API schemas; ran both together, timed a 10,000-row import, and drove the UI in headless Chrome to check screens and the change-salary flow. Bugs found by running it: error handlers passing the status code as the response body (every 4xx came back as 500), and a stale dev server that the frontend agent reported as a backend bug | Had it committed in small steps by area (scaffold, API, tests, frontend, docs); the frontend fills large screens with fluid sizing |
| 15. Packaging | Wrote the production Dockerfile, added the Postgres driver and a `--if-empty` seed mode, ran the image against real Postgres (migrations, 10,000-row seed, login, UI, an import through the worker). Running it on Postgres found a bug the SQLite tests could not: the worker's job claim used `FOR UPDATE` across an outer join, which Postgres rejects, so imports never started; fixed with a lock on the job row only and a test that checks the Postgres SQL. Checked the GoDaddy token without printing it and found the domain is `docrelay.in`, not `docrelay.io` | Chose to keep the deploy code in the skill folder and to switch the domain to docrelay.in |
| 16. First deploy, CI and Deploy button | Ran the first real deploy; it stopped at creating secrets because the AWS CLI can't read `--cli-input-json` from a pipe (the test stubs could), fixed with an owner-only temp file. Wrote CI (backend, frontend, deploy scripts, gitleaks, the image on Postgres) and a Deploy button using a GitHub OIDC role that can't change the infrastructure (corrected in 17: it is still root on the server), with a `--release` mode that starts a stopped server and never needs the GoDaddy token. A gitleaks scan of the history flagged only the fixed test key. First CI run: two tests assumed they weren't on GitHub (fixed); first Deploy run: AWS refused the sign-in because GitHub sends an ID-based subject for this repo (trust rule fixed to match the IDs exactly); the second Deploy run released successfully | Deployed it themselves first, asked for a button instead of deploy-on-push, and moved the permission rule into the project settings |
| 17. Code review | Ran a code review of the whole repo; it found 10 issues the tests didn't cover. Fixed them, each with a test that fails on the old code: a blank import currency switching an employee to the country's currency, a same-day salary correction never taking effect before the start date, unchanged rows of not-yet-started people blocked by the default date, an import crashing when a code or email was taken during review, a starting worker re-queuing another worker's job (now a heartbeat), failed imports keeping the raw file, the rate refresh overwriting "updated by" and rounding differently, a lost response store turning a success into a 500, and docs that understated the deploy role (it is root on the server) | Asked for the whole-repo review and had the fixes checked before pushing: lint, all 170 tests, the new migration run on a Postgres database that already had data, and an import and the rate refresh on real Postgres |
| 18. As-user oracles | Read a reference page on "as-user oracles" (real-browser scenario checks) and checked it against this repo; then built `e2e/`: a Playwright harness with an app gate (the `/health` commit must match the checkout) and a login gate, 11 scenarios across login, People and salary changes, a click path per feature, 18 harness tests, and a CI step against the production image on Postgres. Proved the oracles can fail by breaking the app on purpose: a new `Idempotency-Key` per click turned the retried-save scenario RED, and removing the version check turned the two-admins scenario RED. Found that the salary form dates "today" from the browser's local clock while the server uses UTC | Shared the reference page and asked for it to be built in this repo |
| 19. Oracle skill | Wrote the `as-user-oracles` skill in a separate git worktree (the author was editing the main checkout): a throwaway-app script, a page probe for picking selectors, and the run and create workflows, with bats and pytest tests run in CI. Following its create workflow to add login S4 found a real bug: signing out left a blank page (the pages read a user who had just signed out). Fixed it with a Vitest test that failed first, and showed S4 goes RED on the old code and GREEN on the fix. Running the skill also found two gaps in itself (the probe missed menu items, and read the page before a click had finished), both fixed | Asked for the skill, the worktree, and a PR after a full test run |
| 20. Test and security review | Measured coverage (backend 96%, frontend 55%) and reviewed the code for security by hand (the `/security-review` command needs an `origin/HEAD` this clone doesn't have). Found and fixed: formula injection in the problem-rows CSV (shown with a real request first), two simultaneous uploads both opening an import (now a database index, checked on real Postgres), and signing out blanking the page (found while writing a test for it). Added 42 backend and 120 frontend tests: path traversal, error handlers, idempotency races, filters, import edge cases, the worker loop, the seed command, and every untested page and dialog. Backend coverage is now 99%, frontend 97% | Asked for a full test and security check, then for all the suggested fixes, run but not committed |
| 21. Index check | Ran `EXPLAIN ANALYZE` on 22 of the app's real queries (compiled from the repository code) against a seeded Postgres copy. Most already used an index; "recent salary changes" sorted every salary entry (23.8 ms) and the job-title filter couldn't use its index (2.4 ms). Added both indexes in migration 0004 with SQLite plan tests, re-ran the plans on Postgres (0.07 ms and 0.5 ms) and round-tripped the migration | Asked whether the tables were indexed, then for the EXPLAIN check and the two indexes |
| 22. Async backend | Explained why the backend was sync (the reason was in 04-BACKEND.md, which it first missed), recommended measuring before switching, then converted the backend in a separate git worktree when asked: async endpoints, `AsyncSession`, an asyncio worker and seed script, blocking calls moved to threads, and the 222 tests moved to `pytest-asyncio`, plus a rule that fails any test with an un-awaited coroutine (it first checked that the rule works, and found the warning alone let tests pass). The conversion found two bugs: the idempotency race path read the user after a rollback, which an async session can't reload (it would have been a 500), and moving an employee to another department returned the old department's name, also in the sync code (shown with a test run against the unchanged code). Ran the real app and worker on Postgres 16 with the 10,000-employee seed: 33 checks over HTTP, including an import through the worker, 100 requests at once and a clean SIGTERM stop. Then ran every test suite (backend, frontend, e2e harness, both skills, 12/12 browser oracles) and benchmarked sync against async with ApacheBench on the same Postgres: async served 13–43% more requests a second at 10–50 at once, no clear difference one at a time, and at 100 at once the sync server stalled (requests waited 30 s for a database connection and failed) while async had no errors | Asked for async against the recommendation, and for the work on its own branch in a worktree |
| 23. Wake page | Found why the demo URL timed out (the server was stopped by its 4-hour auto-stop; DNS and the deploy were fine), proposed wake-on-visit options, then built the chosen one: a Lambda wake page at `wake.acme.docrelay.in` behind a shared wake code, the certificate and DNS steps in `deploy.sh`, and an auto-stop scheduled at every boot (without it a woken server would never stop). 30 pytest and 17 new bats tests; broke the code five ways on purpose to check the tests fail; drove the real page in headless Chromium against a local fake of AWS (wrong code, start, wait, redirect) | Asked for the wake page and chose the shared code over expiring links and Cognito |
